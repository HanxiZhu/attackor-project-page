01

Why OR-specific context?

On Qwen3.5-9B-SFT, unrelated sentences lower Pass@1 by 2.74 points; AttackOR perturbations lower it by 20.51 points. Off-topic text rarely resembles a real modeling instruction. Our distractors instead draw on the instance's entities, attributes, quantities, and units.

02

Why keep the ground truth fixed?

An admissible attack preserves the original optimization task: the real options' feasible region, objective, and correct answer. Clean and attacked inputs can then share one evaluation target, so a performance drop reflects misreading the added noise rather than a changed problem.

Attack design

Apply each change separately to the same A/B/C allocation problem above. Two attacks test semantic interpretation; two test equivalent numerical expressions.

01

Attribute injection

Insert a plausible, non-operative attribute that looks actionable.

Example · Add “B is typically preferred for fragile goods.” This is context, not a rule. A model that fills B first (B = 80, A = 40) pays $560 instead of $520.

semantic
02

Phantom options

Add a cheap extra option that a separate condition makes unusable.

Example · Add warehouse D (capacity 80, $3/crate), but operating D requires one loading permit and none are available. Thus D = 0. Ignoring that condition suggests an invalid $400 plan (D = 80, A = 40).

semantic
03

Arithmetic equivalence

Rewrite values as arithmetic expressions with the same result.

Example · Write demand as 3 × 40 crates and A's capacity as 4 × 20 crates. They still mean 120 and 80; the optimal allocation stays A = 80, B = 40.

numeric
04

Unit conversion

Express the same quantities in a different measurement unit.

Example · At 10 kg per crate, describe A's capacity as 800 kg and demand as 1,200 kg instead of 80 and 120 crates. After conversion, the same $520 solution follows.

numeric
How the three-level OR attribute library builds semantic attacks

The library is built from OR benchmark questions: identify recurring domains, collect entity types within each domain, then extract plausible attributes for each entity. Generic attributes at the domain level serve as a fallback.

Domaintransportation→Entitywarehouse→Attributeautomation level

Each attribute has a name, description, unit, and usage example. For a new question, the system matches its domain and entities before selecting an attribute.

Attribute injection

Choose an attribute that is plausible for the matched entity but irrelevant to this optimization task. Generate an instance-scaled value and weave the attribute into the question as background information; the generated text is checked for obvious new constraints.

Phantom options

Select an attribute that can act as a scarce resource. Generate an attractive, format-matched extra option, then add a condition requiring that resource when it is unavailable. The new option looks competitive but cannot be used.

03 /

From attack to defense

STAGE I

OR-specialized SFT

Fine-tune Qwen3.5-9B on 3,000 OR-Instruct examples to generate executable optimization programs. This is the starting policy for robustness training.

STAGE II

Interference-aware GRPO

Train on adversarially augmented instances. An analyzer identifies the distractor and intended defense behavior; a separate judge uses that analysis to score whether generated code resisted the attack.

Training signal

Rtotal = Plen + 0.2 Rformat + 0.3 Rexec + Racc + Rdef

The reward checks Python format, solver execution, objective-value accuracy (5% relative-error tolerance), and attack defense. The defense term uses analyzer context; it is set to zero for clean rollouts. The analyzer and judge are used during training, with no added inference-time component. Format, execution, and accuracy checks must pass before the defense judge is called.

Training data and configuration

Stage I uses 3,000 OR-Instruct examples. Stage II combines clean and attacked OR instances, shuffled with seed 42 and split 80/10/10. The AttackOR benchmark contains 5,240 adversarial examples.

Stage I · SFT

The SFT data use prompt/completion pairs: the prompt states the OR question and asks for a mathematical model and coptpy code; the completion contains the model explanation and solver code. Loss is computed on the completion only.

Training uses full-parameter fine-tuning with DeepSpeed ZeRO-3 and bf16: 3 epochs, 8 GPUs, global batch 128, learning rate 5×10⁻⁵. The combined prompt and completion are truncated at 14,096 tokens.

Stage II · GRPO

Each training row contains a user-question prompt, a numerical optimal-value ground truth for reward scoring, and attack type plus defense rationale as metadata. The ground truth and rationale are not included in the actor prompt.

VERL/vLLM: prompt limit 3,000 tokens, response limit 4,000 tokens, 6 rollouts per prompt, 15 epochs, global batch 128 on 6 GPUs. Overlong prompts raise an error rather than being silently truncated. Thinking mode is not explicitly disabled.

Scope and next questions

AttackOR measures input-level robustness for single-turn OR code generation.

The paper's attack space covers four realistic, semantics-preserving families, not every way an optimization workflow can fail. Structural changes to the mathematical task, multi-turn clarification, solver invocation, and downstream interpretation remain outside this evaluation.
